# opt_explore 方案设计

## 背景与动机

### 问题

当前 `model_opt` skill 沉淀了一套成熟的方法论框架(四维度、五种分析模式、瓶颈四分类、等价替换三层搜索等),`evidence_db` 的 schema 也完全绑定在这套框架上。这带来一个风险:**agent 只会记录框架能解释的东西**,框架外的新发现——比如现有四维度覆盖不了的优化手段、预想不到的 NPU 行为、全新的分析角度——会被框架过滤掉或硬塞进不合适的字段。

长此以往,知识库变成方法论的"自我印证",而非新知识的发现渠道。

### opt_explore 的定位

`opt_explore` 是一个**探索性 skill**,与 `model_opt` 并行存在:

- **相同点**:核心工作流一致(采集 → 分析 → 优化 → 精度验证 → 性能验证 → 知识记录)
- **不同点**:分析和优化的具体方法**不预设框架**,让 agent 自由发挥;知识库记录**开放格式**,专门捕获框架外的新发现
- **关系**:opt_explore 是 model_opt 的"探索前沿",model_opt 是"成熟方法论的固化"。opt_explore 中反复出现、验证有效的新方法,可以被提炼吸收回 model_opt 的方法论框架中。

```
opt_explore (自由探索,捕获新发现)
     ↓ 反复验证有效的新方法
model_opt (固化方法论,结构化指导)
```

---

## opt_explore 的核心工作流

与 model_opt 的 Phase 结构对齐,但每个 Phase 的约束不同:

### Phase 1: 前期准备

与 model_opt 基本一致(这部分没有"方法论自由发挥"的需要):
- 理解模型代码、搭建 NPU 环境、准备测试数据
- 构建 profiling 采集脚本(agent 自行构造,标准的 torch_npu.profiler 采集即可)
- 采集基线性能数据
- 构建精度验证脚本

**唯一约束**: 基线必须可复现(固定输入、固定 seed、记录环境)。

### Phase 2: Profiling 分析(自由发挥)

**不预设任何分析框架**。agent 自行决定:
- 采集什么数据(哪些 profiling level、哪些文件)
- 怎么分析(用什么脚本、读什么原始数据、做什么推理)
- 得出什么结论(不强求归入四分类,不强求用五种分析模式)

**唯一约束**: 分析过程必须**可追溯**——记录"看了什么数据、怎么推理的",不能只给结论。即使推理路径不符合任何已知框架,也要如实记录,因为那可能就是新发现。

### Phase 3: 优化实施(自由发挥)

**不预设优化手段分类**。agent 自行决定:
- 用什么手段优化(可以是四维度之内的,也可以是框架外的)
- 怎么实施(改代码、改配置、换实现、调参数……)
- 每步改动后做快速精度验证

**唯一约束**: 每个改动都要能回答"为什么觉得这会有效"——即使理由是直觉或假设,也要如实记录假设。失败的假设同样有价值。

### Phase 4: 验证(保留)

与 model_opt 完全一致——这是不可妥协的:
1. **精度验证**: 与 baseline 对比,确认无退化
2. **性能验证**: 与基线对比,确认收益

验证方法和 model_opt 的 04_accuracy_assurance 复用,不重新发明。

### Phase 5: 知识记录(开放格式)

**这是 opt_explore 与 model_opt 的核心差异点**。记录格式开放,目标是**不丢失任何信息**,特别是框架外的新发现。

## 知识库设计: explore_db

### 与 evidence_db 的区别

| | evidence_db (model_opt) | explore_db (opt_explore) |
|---|---|---|
| schema | 结构化,字段绑定方法论框架 | 开放,agent 自行组织 |
| 目的 | 验证方法论、快速匹配已知路径 | 捕获新发现,不预设什么是有价值的 |
| 归类 | 强制归入四维度/四分类 | 不强制归类,允许"uncategorized" |
| 消费 | 用于检索匹配、反哺方法论 | 用于发现盲区,提炼新方法论回 model_opt |

### explore_db 记录格式

**不设固定 schema,只设最低必填字段**,其余自由发挥:

```yaml
- id: <string>  # 唯一标识,自由命名
  date: <string>  # YYYY-MM-DD
  hardware: <string>  # 硬件+CANN版本(必填,因 NPU 行为随版本变)

  # === 以下全部自由格式,唯一要求: 信息完整、过程可追溯 ===

  # 观察到了什么(agent 自行描述,不限 profiling 文件/指标)
  observations: |
    <自由文本。可以贴脚本输出、可以描述肉眼看到的 pattern、可以记源码结构。
     不限格式,目标是把"agent 看到了什么"完整记下来。>

  # 怎么分析的(agent 的推理过程,不限方法论)
  analysis: |
    <自由文本。记录 agent 从观察到结论的推理链。
     不要求套用五种分析模式;如果用了就说用了,没用就如实记自己的推理方式。
     关键: 如果推理方式不在任何已知框架内,明确标注"novel approach"——这是新发现的种子。>

  # 得出什么结论
  conclusion: |
    <自由文本。根因是什么、属于什么类型(如果类型不在已知分类里,自创一个标签并说明)。>

  # 做了什么优化(自由描述,不限手段分类)
  actions: |
    <自由文本。每个尝试: 做了什么、为什么觉得有效(哪怕只是假设)、
     精度验证结果、性能验证结果、成功还是失败。
     失败的尝试和原因同样重要。>

  # 新发现标记(opt_explore 的核心价值)
  novel_findings: |
    <自由文本。本次优化中出现的、不在 model_opt 现有框架内的东西:
     - 新的分析角度?(框架外五种模式之外的推理方式)
     - 新的优化手段?(四维度之外的优化方向)
     - 新的 NPU 行为?(预想不到的硬件特性)
     - 新的瓶颈类型?(四分类之外的瓶颈)
     如果没有新发现,写"none"。>
```

### 最低必填 vs 自由

**必填**(确保基本可用):
- `id`, `date`, `hardware` — 标识和可复现性
- `observations` — 至少要知道看到了什么
- `conclusion` — 至少要知道得出了什么结论

**自由**(agent 按实际情况组织):
- `analysis`, `actions`, `novel_findings` — 可长可短,可结构化可自由文本
- 允许 agent 新增任意字段(如 `npu_behavior_notes`, `failed_hypotheses` 等),只要信息完整

### 存储位置

与 evidence_db 一致,存在项目工作目录:
```

```

# NPU 推理优化探索

## 定位

本 skill 提供一套探索性的推理优化工作流:核心流程(采集 → 分析 → 优化 →
精度验证 → 性能验证 → 知识记录)固定,但**分析怎么做、优化怎么选不预设
方法**,由 agent 根据实际情况自由发挥。

目标是捕获那些预设框架覆盖不到的东西——新的分析角度、新的优化手段、
预想不到的 NPU 行为——并记录到知识库,作为后续沉淀方法论的原材料。

## 核心原则

- **Profiling 驱动**: 优化决策必须有性能数据支撑,不凭空猜测
- **过程可追溯**: 分析和优化的推理过程必须完整记录,不能只给结论
- **如实记录假设**: 即使优化理由只是直觉/假设,也要写下来;失败的假设同样有价值
- **不强行归类**: 遇到无法归入已有认知的现象/手段,如实标记为"新发现",不要硬套
- **精度不可妥协**: 无论怎么探索,精度验证是硬约束,不允许为性能牺牲正确性

## 工作流

### Phase 1: 前期准备
- 理解模型代码和推理路径
- 搭建 NPU 环境、准备可复现的测试数据(固定输入、固定 seed)
- 编写 profiling 采集脚本,采集一份基线性能数据(全程作为收益判定基准)
- 编写精度验证脚本(离线保存输出,事后 numpy 对比)

约束: 基线必须可复现,记录硬件型号和 CANN/torch_npu 版本。

### Phase 2: 自由分析
采集 profiling 数据,自行决定怎么分析:
- 采什么(哪些数据文件、什么采集粒度)由 agent 判断
- 怎么分析(用什么工具、读什么原始数据、做什么推理)不设限
- 结论不强求归入任何预设分类

唯一要求: 记录"看了哪些数据、如何一步步推理到结论",过程可追溯。
如果推理方式是你临场想出的、不属于常规套路,明确标注为"新分析角度"。


### Phase 3: 自由优化
实施优化,手段不限:
- 可以是常规手段(换实现、预分配、融合、图编译……)
- 也可以是你想到的非常规手段
- 每个改动都记录"为什么觉得这会有效"(哪怕只是假设)
- 每步改动后做快速精度验证,不通过立即回退

### Phase 4: 验证(不可省略)
1. **精度验证**: 与 baseline 对比,确认数值无退化(声明阈值,覆盖边界输入)
2. **性能验证**: 重新采集 profiling,与基线对比,确认确实有收益

任一不通过则回退或调整。

### ★ 用户确认节点 B
向用户展示本批总结(优化点、性能收益、精度数据、未采纳方案及原因),
用 ask_user_question 确认后再提交。

### Phase 5: 知识记录
按 [references/explore_db_schema.md](references/explore_db_schema.md) 将本轮
探索记录到项目工作目录的 `explore_db/` 下(与 `profiling/` 同级)。
重点记录**新发现**——不在常规认知内的分析角度、优化手段、NPU 行为,
是本 skill 最有价值的产出。

## 迭代
一轮优化(Phase 2→4)完成、瓶颈转移后,回到 Phase 2 开启下一轮,
直到性能达标或剩余瓶颈无优化空间。
```

### explore_db_schema.md 内容设计

即上文"explore_db 记录格式"部分,加上填写原则:
- 完整优先,宁冗余勿遗漏
- novel_findings 是核心字段,没有新发现写 none,有则详细描述
- 允许新增任意字段
- 不做检索/消费,纯积累

## opt_explore 与 model_opt 的闭环

```
opt_explore 自由探索
    ↓ explore_db 记录 novel_findings
    ↓ 反复出现、验证有效的新方法
人工/agent 审视: 这个新发现是否应该固化进方法论?
    ↓ 是
提炼回 model_opt:
  - 新分析角度 → 加入 profiling_to_action.md 的五种模式或参考路径
  - 新优化手段 → 加入四维度或新建维度
  - 新瓶颈类型 → 加入瓶颈分类
  - 新 NPU 行为 → 加入脚本自动检测或参考路径
    ↓
model_opt 方法论更新,覆盖更多场景
opt_explore 继续探索下一个前沿
```

**关键**: 这个闭环不是自动的——需要人工判断"这个新发现是否成熟到可以固化"。opt_explore 只负责发现和记录,不负责自动修改 model_opt。
