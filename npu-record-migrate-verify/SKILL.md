# NanoGPT record 迁移与验证

用户点名 record 后，逐个选定已有完整验证的最快达标版本，再迁移、复跑、核对和归档。不要把某个 record 的代码、seed、算子二进制或性能数字套到其他 record；只处理用户点名的范围。

## 站点配置

先从用户或现有可信环境说明确认：源 record 根目录、目标根目录与命名规则、服务器登录方式、Python/CANN/torch_npu 环境、数据路径、NPU 卡数、训练入口以及该任务的精度和训练动态要求。若缺少会改变版本选择或训练结果的条件，先确认，不能凭别的 record 的设置猜。不要把口令、私钥或内网地址写入公开 skill、仓库或运行日志。

## 逐个 record 的工作流

1. **选择已验证的最快达标版本。** 阅读源 record 的结果说明、完整训练日志、源码、启动脚本和优化尝试，建立候选版本与源码/配置/日志的对应关系。先排除未完成全程训练、运行失败、训练任务或 dynamics 不符、最终 val_loss 不达标的候选。以用户给定阈值为准；若明确是要求 `val_loss < 3.28` 的同系列任务，则严格小于 3.28。**仅在合格候选中按已有完整运行的端到端训练时间从短到长排序，选当前最快的版本。** 不按最低 val_loss、最新文件、短跑 step 平均或预计时间选。记录获胜源码路径/哈希、对应日志、时间、val_loss 和配置；证据不足或无合格候选时如实报告，不标记为“最优”。源目录保持只读。
2. **检查目标与环境。** 若目标已存在，先盘点并继续未完成工作，绝不盲目覆盖 `source/`、日志或 `.so`。检查指定数量的 NPU 可见且可用、环境版本、数据和权限。只在确有必要时提权复制源文件，最终训练和目标文件使用预期普通用户；不持久化凭据。
3. **迁移必要文件。** 目标根目录尽量只保留 `run.sh`、中文 `README.md`、`source/`、`logs/` 和必要的 `archive/`。`source/` 放获胜训练代码及其实际依赖；原版可置于 `archive/source/`，对迁移后源码做 diff。只改路径和运行环境所必需的部分；模型、优化器、数据、batch、步数、schedule、seed 等训练 dynamics 不得悄悄改变。启动脚本简短，配置取自本 record 的获胜实验。
4. **按需编译算子。** 如果有自定义 Ascend C，核对源码引用、目标 NPU 架构、CANN/torch_npu 兼容性和实际加载的 `.so`。缺少可用二进制、源码/架构/环境变化或用户要求重编译时，在目标环境从本 record 源码构建，记录命令、日志和哈希于 `archive/build/`；不得借用另一 record 的 `.so`。已有兼容二进制不必每次训练重编译。除非原工作流必须运行时编译，不要将一次性编译混入 `run.sh`。
5. **完整复跑。** 按用户指定卡数和入口启动完整训练；该迁移任务不额外加入精度测试、profiling 或算法调优，除非用户明确要求。先保证日志不覆盖，再等待训练退出，记录实际命令、退出码、最终 val_loss 和端到端时间。按第 1 步的要求再次判定，并与迁移前所选版本的完整结果比较。失败时保留证据并诊断，不能悄悄改选别的版本冒充原最快达标版本；短跑不等于完成。
6. **整理交付。** `logs/` 最终只保留一份能看到最终时间和 val_loss 的完整主日志；指标、UUID/rank 子日志、源码快照与命令等原样归入 `archive/evidence/<运行标识>/`。移动前核对源/目标及冲突，移动后校验哈希，不删除证据。中文 README 写清环境加载、按需编译、运行和结果位置；若未来重跑会重新产生辅助文件，明确说明。交付时报告目标路径、来源与版本选择证据、新旧时间/val_loss 和达标情况。

## 边界

- 不写入源记录、其他 record 或项目根目录；所有新增交付文件归属当前目标 record。不要未经用户要求启动其他 record、提交仓库或改变训练动态。
- 从 Windows 经 SSH 操作时，用 PowerShell 的原生参数数组传参；复杂远端 Bash 脚本避免多层引号误解析。已有 `powershell-safe-invocation` skill 时按其说明执行。
- 迁移验证不等于新一轮性能优化。若用户另行要求调优，再使用相应 NPU 调优流程。
