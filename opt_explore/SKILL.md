# NPU 推理优化探索

## 定位

本 skill 提供一套探索性的推理优化工作流:核心流程(采集 → 分析 → 优化 → 精度验证 → 性能验证 → 知识记录)固定,但**分析怎么做、优化怎么选不预设方法**,由 agent 根据实际情况自由发挥。

目标是捕获那些预设框架覆盖不到的东西——新的分析角度、新的优化手段、预想不到的 NPU 行为——并记录到知识库,作为后续沉淀方法论的原材料。

## 核心原则

- **Profiling 驱动**: 优化决策必须有性能数据支撑,不凭空猜测
- **过程可追溯**: 分析和优化的推理过程必须完整记录,不能只给结论
- **如实记录假设**: 即使优化理由只是直觉/假设,也要写下来;失败的假设同样有价值
- **不强行归类**: 遇到无法归入已有认知的现象/手段,如实标记为"新发现",不要硬套
- **精度不可妥协**: 无论怎么探索,精度验证是硬约束,不允许为性能牺牲正确性

## 工作流

### Phase 1: 前期准备

- 理解模型代码和推理路径
- 搭建 NPU 环境、准备可复现的测试数据(固定输入、固定 seed)
- 编写 profiling 采集脚本,采集一份基线性能数据(全程作为收益判定基准)
  - 使用 `torch_npu.profiler.profile` 接口,按需选择 activities/with_stack/record_shapes/profile_memory 等参数
  - 输出保存到 `<workspace>/profiling/<timestamp>/`,每次采集带时间戳
- 编写精度验证脚本
  - GPU 和 NPU 分别离线保存推理输出(numpy/json)
  - 事后纯 numpy 对比(cosine similarity + max_abs_diff)
  - 固定输入,确保可复现

**约束**: 基线必须可复现。记录硬件型号、CANN 版本、torch_npu 版本。

### Phase 2: 自由分析

采集 profiling 数据,自行决定怎么分析:
- 采什么(哪些数据文件、什么采集粒度)由 agent 判断
- 怎么分析(用什么工具、读什么原始数据、做什么推理)不设限
- 结论不强求归入任何预设分类

**唯一要求**: 记录"看了哪些数据、如何一步步推理到结论",过程可追溯。如果推理方式是临场想出的、不属于常规套路,明确标注为"新分析角度"。

### ★ 用户确认节点 A

向用户展示分析结论和优化方案清单,每条含:
- 优化内容
- 预期收益
- 风险
- "为什么觉得有效"的理由(可以是假设)

使用 `ask_user_question` 确认。仅实施用户确认的条目。

### Phase 3: 自由优化

实施优化,手段不限:
- 可以是常规手段(换实现、预分配、融合、图编译……)
- 也可以是非常规手段
- 每个改动都记录"为什么觉得这会有效"(哪怕只是假设)
- 每步改动后做快速精度验证,不通过立即回退

### Phase 4: 验证(不可省略)

1. **精度验证**: 与 baseline 对比,确认数值无退化
   - 声明阈值(如 cosine >= 0.9999, max_abs_diff < 1e-4)
   - 覆盖多组输入(最短/中位/最长/边界)
   - 确认 NPU 确定性(同输入两次运行 bit-exact)
2. **性能验证**: 重新采集 profiling,与基线对比,确认确实有收益

任一不通过则回退或调整。

### ★ 用户确认节点 B

向用户展示本批总结:
- 实施的优化点及实际效果(性能数据 + 精度数据)
- 未采纳的方案及原因(包括失败的尝试)

使用 `ask_user_question` 确认后再提交。

### Phase 5: 知识记录

按 [references/explore_db_schema.md](references/explore_db_schema.md) 将本轮探索记录到项目工作目录的 `explore_db/` 下(与 `profiling/` 同级)。

重点记录**新发现**——不在常规认知内的分析角度、优化手段、NPU 行为,是本 skill 最有价值的产出。

## 迭代

一轮优化(Phase 2→4)完成、瓶颈转移后,回到 Phase 2 开启下一轮,直到性能达标或剩余瓶颈无优化空间。

## 退出条件

- 性能达到预设目标
- Profiling 显示剩余瓶颈已无优化空间
- 进一步优化的边际收益不值得尝试
