# explore_db 知识库记录格式

## 定位

本文件定义探索性优化的知识记录格式。Agent 在每轮优化(Phase 2→4)完成后,按此格式将全过程记录到项目工作目录的 `explore_db/` 下。

> **路径约定**: 知识数据存在**项目工作目录** `<workspace>/explore_db/`(与 `profiling/` 同级),不在 skill 目录中。

## 设计原则

- **开放格式**: 只设最低必填字段,其余自由发挥——不预设什么信息有价值
- **完整优先**: 宁可冗余不可遗漏,不确定有没有用的信息一律记下来
- **过程可追溯**: 不只记结论,还要记"怎么推理到这个结论"
- **新发现优先**: `novel_findings` 是核心字段——框架外的新东西是本知识库的最大价值
- **失败必记**: 失败的假设和尝试与成功一样有价值

## 记录格式

每个案例一个 YAML 文件,文件名 = `id` 字段值 + `.yaml`。

### 必填字段

```yaml
id: <string>
  # 唯一标识符,自由命名
  # 建议格式: <模型缩写>-<核心主题>-<日期YYYYMMDD>
  # 例: "qwen7b-compile-stall-20260706", "deepseek-moe-routing-20260710"

date: <string>
  # YYYY-MM-DD

hardware: <string>
  # 硬件型号 + CANN/torch_npu 版本
  # 例: "Ascend 910B / CANN 8.0.0 / torch_npu 2.3.1"

observations: |
  # agent 观察到了什么(自由文本)
  # 可以贴脚本输出、可以描述肉眼看到的 pattern、可以记源码结构
  # 不限格式,目标是把"agent 看到了什么"完整记下来
  # 原始数据摘录比概括更好——细节日后可能有用

conclusion: |
  # 得出什么结论(自由文本)
  # 根因是什么、属于什么类型
  # 如果类型不在任何已有分类里,自创一个标签并说明
```

### 可选字段(建议尽量填)

```yaml
analysis: |
  # 怎么分析的(agent 的推理过程,自由文本)
  # 记录从 observations 到 conclusion 的推理链
  # 不要求套用任何框架;如果用了某种套路就说,没用就如实记自己的推理方式
  # 关键: 如果推理方式是临场想出的新方法,明确标注

actions: |
  # 做了什么优化(自由文本)
  # 每个尝试:
  #   - 做了什么
  #   - 为什么觉得有效(哪怕只是假设)
  #   - 精度验证结果
  #   - 性能验证结果
  #   - 成功还是失败
  #   - 如果失败: 为什么失败
  # 失败的尝试和成功的一样详细记录

novel_findings: |
  # 新发现(自由文本)——本知识库的核心价值字段
  # 本次优化中出现的、不属于常规认知的东西:
  #   - 新的分析角度?(不在常规套路内的推理方式)
  #   - 新的优化手段?(常规手段覆盖不到的方法)
  #   - 新的 NPU 行为?(预想不到的硬件特性)
  #   - 新的瓶颈类型?(不在已有分类内的瓶颈)
  # 如果没有新发现,写"none"
  # 有新发现时详细描述: 它是什么、怎么发现的、为什么说它是"新的"
```

### 允许新增任意字段

agent 认为需要记录的额外维度,可自行新增字段。例如:

```yaml
npu_behavior_notes: |
  # 观察到的 NPU 特殊行为(非预期的硬件表现)

failed_hypotheses: |
  # 被证伪的假设清单(假设内容 + 证伪证据)

source_code_insights: |
  # 对模型源码结构的理解(哪些代码路径是关键路径)

comparison_with_gpu: |
  # 与 GPU 行为的对比差异
```

这些自定义字段不影响基本格式,信息越完整越好。

## 目录结构

```
<workspace>/
├── profiling/       # profiling 数据
├── explore_db/      # 探索知识库(项目工作目录下)
│   ├── <id>.yaml    # 每个案例一个文件,扁平存放
│   └── ...
└── ...
```

## 填写时机

每轮 Phase 2→4 完成后,无论优化成功还是失败,都写一个案例文件。一轮一个文件。
