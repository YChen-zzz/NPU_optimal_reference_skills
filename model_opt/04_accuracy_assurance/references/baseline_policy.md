# 基线管理策略

## 问题

精度对比的前提是有一个可信的 baseline。如果 baseline 来源不对，整个对齐结论无效。

## 基线来源优先级

按以下顺序确认，不可跳过：

1. **官方或任务指定基线**：标准结果、保存的 checkpoint/输出和评价脚本
2. **迁移源基线**：用户提供的 GPU/common-source 输出与最终任务指标
3. **NPU 优化前自身基线**：当上游结果不可得时，用于判断优化是否改变已有语义
4. **CPU 调试结果**：只用于定位 PyTorch/NPU 路径问题，不默认作为最终结论

## 强制规则

- **先查官方基线，再写对比脚本**：不要进入精度对比流程后才发现基线来源不对
- **自动发现**：先搜索 README、配置、日志、checkpoint、输出、评价脚本和 evidence manifest；已有可信基线直接复用
- **自主降级**：上游基线不可得时，保存一次优化前 NPU 输出和任务指标，并在报告中标记结论边界；不因此阻塞内部优化循环
- **禁止默认 CPU 作为最终基线**：CPU 路径容易跑通不代表它是官方基线
- **阈值必须在比较前声明**：不能先看到 mismatch，再临时放宽阈值后写成“全部对齐”
- **样例级对齐 ≠ 模型级对齐**：官方示例只能证明示例覆盖范围内的结果一致

## CPU 对比的合法用途

仅以下情况可以做 CPU 对比：
- 用户明确要求
- 官方文档明确把 CPU 结果作为标准
- 仅作为本地调试辅助（报告中必须标注“仅用于调试，不作为最终对齐结论”）

## 何时需要外部输入

只有缺失信息会改变任务的验收语义、且无法从源码、配置或现有产物恢复时，才请求用户提供最终评价指标或基线位置。缺失 GPU Teacher 性能证据不等于缺失 accuracy baseline；两者分别记录。

## 报告措辞

- 只做了 CPU 对比：“当前仅完成 CPU vs NPU 调试性比较，不作为最终精度对齐结论”
- 只对齐了官方示例：“官方示例级推理结果基本对齐，尚未覆盖完整评测集”
