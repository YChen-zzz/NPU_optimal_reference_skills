# 主动源码分析(Line A)

### 目标

从代码出发,用四维度思维框架主动发现优化机会——不依赖 profiling 异常信号。

很多高价值优化点(QKV 合并、KV cache 预分配、cross-attention 预计算)在 profiling 中看不出异常(每个算子单独看都正常),只有理解代码结构才能识别。

### 穿透框架层

很多模型的推理路径被框架层层包裹,直接看入口代码看到的是框架调度逻辑而非模型计算。agent 必须穿透框架到达真实的模型实现代码。

**识别框架 wrapper**:看到 `model.generate()` / `trainer.predict()` / `pipeline()` 时,不要停在这里——这是框架入口,不是模型逻辑。

**定位真实 forward**:沿调用链向下,跳过 `Module.__call__` / hook dispatch / mixin 方法,找到项目自己的 `modeling_xxx.py` 中的 `forward()` 实现。

**区分两类代码**:
- 框架代码(site-packages 下):调度/hook/logging/兼容性处理——这里的开销属于 Line B 分析(dispatch overhead)
- 模型代码(项目目录下):真实的计算逻辑——这里的结构性冗余属于 Line A 分析

**常见框架穿透路径**:
- HuggingFace: `generate()` → `_generate_*()` → `model()` → `modeling_xxx.py:XxxModel.forward()`
- vLLM: `LLMEngine.step()` → `model_runner.execute_model()` → `model.forward()`
- 自定义脚本: `main()` → `model(input)` → 找到 `nn.Module` 子类的 `forward()`

#### 穿透层级量化

推理调用链从外到内分为多层，每层都可能贡献 host 开销。不要只分析 `forward()`——**每一层**都要量化。

1. 从入口到算子，列出调用链经过的所有层（如 `generate()` → `Module.__call__` → `forward()` → `F.linear` → `aten::matmul`）
2. 用 `parse_operator_details.py` 的 host self duration 数据，量化每层的 host 开销占比
3. 记录每层占比，供确认节点 A 的优先级覆盖门禁使用

> 注意：此步骤只做**量化记录**，不在此处提出方案。某层占比高意味着该层有优化空间，具体怎么改是 Phase 3 的工作。

### 三层分析对象

**1. 模型结构层**:模型由哪些组件构成、怎么组织
- 注意力类型(MHA/GQA/MQA/cross-attention)、FFN 结构、Norm 选择
- 重复结构(N 层循环、共享权重)、生成模式(autoregressive/diffusion/encoder-decoder)
- 这一层回答"模型是什么"

**2. 实现逻辑层**:具体代码怎么实现这些组件
- 数据流路径:tensor 从输入到输出经过哪些变换,有没有绕远路
- 生命周期管理:哪些中间结果被创建后立即丢弃、哪些跨步复用
- 控制流:哪些分支在推理时永远走/永远不走、哪些条件判断是多余的
- 这一层回答"代码怎么做的,有没有浪费"

**3. 算法层**:当前的计算方法是否有更优的等价实现
- 同一功能是否存在计算复杂度更低的算法
- 是否有硬件更友好的等价表达(不改功能但改实现路径)
- 这一层回答"有没有更好的做法"

### 四维度驱动提问

通读源码后,对每个计算逻辑块用四维度主动提问。

> **边界**:Phase 2 的四维度用于**发现问题**(问"有没有机会"),不展开"怎么改"。具体实施手段(如何合并、如何预分配、用哪个融合算子)是 Phase 3 的工作,由 03_optimization 的各 reference 承载。这里只需识别出"这里存在去重/复用/掩盖/替换的机会"并量化值不值得做。

**去重**:这段计算有没有多余的工作?
- 有没有重复调用(同一输入的多次独立计算可合并)?
- 有没有死逻辑(推理时不产生效果的分支)?
- 有没有不必要的数据变换(绕了一圈又变回来)?

**复用**:这段计算的结果/资源有没有被浪费?
- 有没有每步都重新计算但结果不变的东西(可预计算)?
- 有没有每步都分配释放同一块内存(可预分配复用)?
- 有没有跨步/跨层可以共享的中间结果?

**掩盖**:这段延迟有没有机会藏起来?
- 有没有串行但互不依赖的计算(可并行/重叠)?
- 有没有可以和通信重叠的计算段?

**替换**:这段计算有没有硬件更友好的等价写法?
- 有没有更高效的算法(如标准 attention → FlashAttention)?
- 有没有 NPU 融合算子可覆盖这组计算?
- 当前 API 在 NPU 上是否有更优的等价表达?

### Profiling 量化(筛选候选)

Line A 发现的候选点需要 profiling 数据量化"值不值得做":
- 识别到某组 Linear 可合并 → 查 op_statistic:这些 Linear 分别占多少时间? 合并的理论收益?
- 识别到某结果每步重算 → 查 operator_memory/op_statistic:重算占总时间多少?
- 如果占比极低(如 <1%)→ 不值得追,跳过

### 热路径操作审计表

对推理热路径（每步/每 token 执行的代码）中的**每个操作**，填写四维度审计表。这是四维度提问的结构化形式——强制对每个操作逐一思考，不能只对"显眼"的操作提问而跳过其余。

| 操作 | 去重：有多余工作? | 复用：输出随输入变? | 可预分配? | 替换：有融合算子? |
|------|-----------------|-------------------|----------|-----------------|
| _______ | _______ | _______ | _______ | _______ |
| _______ | _______ | _______ | _______ | _______ |

**分析方法**：
- "复用"列：判断操作的输出是否只依赖模型参数或序列形状（不依赖输入内容）。若是，标记"否(不随输入变)"
- "可预分配"列：判断操作的输出 shape 在热路径中是否固定。若是，标记"是"。结合 `parse_operator_memory.py` 数据确认是否存在重复同尺寸分配
- "替换"列：检查该操作的算子序列是否构成已知的可融合 pattern。用 `[x for x in dir(torch_npu) if 'npu_' in x.lower()]` 发现可用算子，对照 [npu_operator_reference.md](../../03_optimization/references/npu_operator_reference.md) 确认 dtype/shape 约束
- "去重"列：检查是否存在同一输入的多次独立计算、推理时永不走的分支、绕一圈又变回来的数据变换

> 此表是**分析工具**——识别"哪里存在机会"。表中标记为"是"或"否(不随输入变)"的条目意味着该维度有优化空间，但是否值得做、怎么做由后续 profiling 量化和 Phase 3 决定。

### 产出

Line A 的产出是一份"源码问题候选清单",每条含:
- 识别到的问题(如"Q/K/V 三个 Linear 共享同一输入但独立调用")
- 问题位置(源码文件 + 函数/行号)
- profiling 量化的影响范围(如"这三个 Linear 共占 device time 8%")

> 不在此阶段给出解决方案——"怎么改"是 Phase 3(03_optimization)的职责。
